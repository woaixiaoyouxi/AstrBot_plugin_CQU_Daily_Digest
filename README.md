# 每日简报（重庆大学）

把散落在各处的信息整合成一份按点推送的简报：

- **校内通知** —— 教务处 / 学院 / 图书馆等站点的网页通知
- **校外竞赛** —— 竞赛通知
- **QQ 群消息** —— 监听指定群，把群里的通知一起收进来
- **今日天气** —— 来自 [wttr.in](https://wttr.in)，无需 API key
- **即将截止** —— 从条目库里挑出快过期的，提前提醒

推送形态是**合并转发卡片**（像一条转发出来的聊天记录，点头部展开看），不是一大段纯文本；协议端不支持时自动退回纯文本。

群里的**任何人都能主动来查**一份（需管理员先开放该群，见[权限](#六权限)）。

> **本插件不含任何登录态**，只抓公开网页 + 监听群消息。

## 一、它做什么

### 1.1 每条通知长什么样

模型把抓到的原始网页整理成固定格式。**原文没写的字段整行省略**，不写「未提及」，也不推测：

```
[关于举办 2026 年数学建模竞赛的通知]
内容简述：面向全校本科生，三人一队，需一名指导教师
时间：26/10/15（报名截止）
地点：虎溪校区理科楼
链接：https://example.edu.cn/notice/1234
要求：在校本科生，组队报名
能获得什么：校级一等奖可认定创新学分
```

字段顺序固定：`[标题]` → `内容简述` → `时间`（可多行，每行地点配套）→ `地点` → `链接` → `要求` → `能获得什么`。

时间用 `YY/MM/DD` 格式；如果是截止日，括号里注明。

### 1.2 摘什么，由模型判断

抓到的通知不是照单全收。提示词里写明了**只留在校本科生相关的**：能报名的活动、竞赛、讲座、文体比赛、志愿服务；评奖评优；选课考试学籍；宿舍食堂校园卡网络水电校内交通医疗安全这类生活后勤。

人事任免、招标采购、财务审计、基建修缮、会议纪要、党务巡视、科研项目申报、学报与学术委员会、校友基金会、离退休工会这类行政公文由模型略去。**拿不准就留下**——宁可多一条，也别漏掉学生真用得上的。

判断依据是通知的标题**和正文**，所以 `fetch_body_campus` 建议保持开启。

### 1.3 两处「绝不」

这两条是刻意的，别改成「看起来更全」的样子：

1. **模型返回空时，绝不退回纯列表。** 否则会把刚筛掉的行政公文原样倒出来。
2. **查询本身不写去重基线。** 否则群友查一次就记成「已推送过」，你自己反而收不到。唯一的例外：群友查到新通知、管理员也确实收到了，这时才补记（详见 [2.5](#25-公开查询与定时推送有什么区别)）。

### 1.4 降级行为（都会告诉你原因）

- 模型调用失败 / 超时 → 降级成纯列表，**且不过滤**，把抓到的全列出来（宁可多给，不可漏掉）
- 合并转发失败 → 退回纯文本，并在回复里写明原因（日志文件默认是关的，只写日志你看不到）

## 二、它怎么工作

### 2.1 模块分层

```
入口层    main.py          注册 / 生命周期 / 指令分派 / 群消息监听
          commands.py      7 条指令 + 公开查询的闸门（权限 / 冷却 / 排队）

编排层    pipeline.py      抓取 -> 筛 -> 调模型 -> 写库 -> 发
          push.py          唯一发消息出口（卡片 / 降级 / 通知管理员）
          renderer.py      拼 prompt / 调模型 / 排版 / 提醒渲染
          group_collector  群消息采集与编排（读缓冲、读配置）
          schedule / config

数据层    entries.py       条目格式的唯一真源（正向解析 + 反向渲染）
          blocks.py        群消息块算法（零依赖纯函数）
          storage.py       KV + 条目库

外部      fetch/           engine(httpx+bs4) / sources / parsers / weather
          base.py          零依赖纯定义（CHINA_TZ、Notice）
```

设计上的几条硬规矩：

- **`base.py` 和 `blocks.py` 零依赖**（一个 import 都不用），所以能脱离 AstrBot / httpx / bs4 单独跑测试
- **底层不依赖抓取层**：`config` / `schedule` / `storage` / `entries` / `auth` 里出现 `fetch` / `httpx` / `bs4` 就算错。这条由测试守着
- **互为逆操作的代码放一起**：`split_entries`（文本→结构）和 `entry_block_text`（结构→文本）都在 `entries.py`。改格式必须同时改这两个，分开写迟早漏一边，而且是静默的
- **概念只住一个文件**：「块」只在 `blocks.py`、「条目格式」只在 `entries.py`、「发消息」只有 `_send_one`

### 2.2 一次推送的 11 步

```
 1  抓网页（校内通知 / 竞赛两个源）
 2  读 seen_ids -> 算出「哪些是新的」
 3  窗口过滤（命令式查询按 query_recent_days 卡；定时推送不卡）
 4  补正文（按开关给需要正文的条目抓详情页，单条失败降级为仅标题）
 5  群消息聚成「块」（同群 + 相邻间隔 + 可选同一发送者）
 6  调模型 -> 按固定格式输出条目
 7  解析成品文本 -> 结构化条目 -> 写条目库
 8  清理过期条目（有截止日过期 N 天 / 没截止日入库超 M 天）
 9  插【即将截止】（条件：在 seen_ids 里 且 距今 0~deadline_alert_days）
10  发出去（合并转发优先，失败退回纯文本并说明原因）
11  真跑才写：seen_ids / last_run_date / 上次简报
```

**第 6 步只喂「新的那几条」**，不是全部候选。今天有 2 条新的，就只喂 2 条；一条新的都没有，**连模型都不调**。

**第 9 步和正文天然互斥**：正文只列新抓的，提醒只列已推过的，不会重复。

### 2.3 群消息怎么变成「一条通知」

通知群里发一条通知常常是分好几条：

```
10:00  张三：【通知】关于举办数学建模竞赛的通知
10:00  张三：报名截止 10 月 15 日，三人一队
10:01  张三：[海报图片]
```

**「块」就是把这些合成一个整体**，好让「这是不是一条通知」的判定有完整上下文。

聚合规则：**同一个群 + 相邻两条间隔 ≤ `group_aggregate_minutes`（默认 10 分钟）+ （默认）同一个人发的**。

为什么要「同一个人」：只看时间的话，通知后面的群友回复（「收到」「我也想去」）会落进同一个窗口，整块被模型判成「是通知」一起转出去。代价是两个人接力发的一条通知会被拆开——但拆开只是分成两条、不丢内容，所以留了开关 `group_block_same_sender` 能关掉。

**「结」关块**：群里有人发「结」「已截止」「结束」这类收尾词时，把对应的块标记为已关闭，不再进简报。三种判法：

| 形态 | 判据 |
|---|---|
| 引用回复了某条 | 关掉被引用那条所在的块 |
| 跟在通知后面（不是块的第一条） | 关掉自己所在的块 |
| 单独发一条 | 关掉该群里上一个还没关的块 |

词表可以在面板里改（`group_end_keywords` / `group_end_contains`），留空用内置的。

**输出**：被保留的块，除了照常生成一条格式化的条目，还会在它下方嵌一张**内嵌卡片**——点开就是这个块的原始消息（谁说的、原文、图片）。所以别人看到的是「一条通知」，需要细节时能点进去看原文。

机器人自己发的消息不会入库（有的协议端会把自身消息也回显过来，那样简报的群消息段会把自己的推送再卷进去）。

### 2.4 条目库和到期提醒

**条目库**是一张账本：每次生成简报时把结构化条目存下来（按 id 覆盖，上限 400 条），所以：

- 同一个通知重复抓到不会重复入库（id 稳定）
- 有些通知的截止日在一个月后，刚推的时候不着急，但**该在快到的时候提醒一次**
- `/digest all` 能直接把整个库拼出来发给你，**零模型消耗**

**「有效」的定义**：有截止日且未过 / 没有截止日且入库不超过 `no_due_expire_days`（默认 30 天）。

**【即将截止】** 的挑选条件：`id 在 seen_ids 里`（= 已经推给你看过）**且** `0 ≤ 距今 ≤ deadline_alert_days`（默认 7 天）。

### 2.5 公开查询与定时推送有什么区别

| | 定时推送 | `/digest`（公开查询） |
|---|---|---|
| 触发 | 每天 `push_time` | 群里任何人发指令 |
| 发到哪 | `push_targets` 里列的会话 | 只回当前会话，绝不外发 |
| 内容 | 新的通知 + 群消息 + 提醒 | **只有增量**；没有新的就回「新增 0 条」 |
| 写 seen_ids | 写 | **不写**（唯一例外见下） |
| 消费群缓冲 | 消费（推过的就清掉） | 不消费 |
| 写条目库 | 写 | 也写（这样 `/digest all` 能攒起来） |
| 冷却 | 无 | `query_cooldown_seconds`（默认 120 秒） |

**唯一的例外**：群友这次查到了新通知，插件会同时给管理员私聊发一份（「群友查到新的消息了！」+ 同一份卡片，开关 `query_notify_admin`）。**只有这条通知确实送到管理员手上了**，才补记进 seen_ids —— 不补的话每天定时推送会再推一遍。发送失败就不记，留给定时补。

**排队**：耗时的入口（`/digest`、`all`、`now`、`test`）进来先回一句「已收到请求，正在生成…」；前面有人在跑就报「排队在第 N 位」；排队人数超过 `queue_limit` 直接劝退。

## 三、安装

放进 AstrBot 的 `data/plugins/` 目录，然后**在面板点「重载插件」或重启 AstrBot**。

> 插件目录只在启动时扫一遍。**光把文件夹拷进去、不重载，列表里是不会出现的**——这一点很容易踩。

依赖见 `requirements.txt`（`httpx`、`beautifulsoup4`），多数 AstrBot 实例自带。

## 四、配置

全部在 AstrBot 面板 →「插件」→ 每日简报 →「配置」。**7 组共 39 项**。

### 推送（8 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `push_time` | `"09:00"` | 每天推送时间，24 小时制。**用半角冒号**（全角也认，但别给自己找麻烦） |
| `push_enabled` | `true` | 关掉就完全不定时推送 |
| `catch_up_on_start` | `true` | 启动时若已过点且今天没推过，补推一次 |
| `push_targets` | `[]` | 推到哪些会话。**手填**，没有自动登记 |
| `max_digest_chars` | `3500` | 正文超过这个长度截断 |
| `use_forward_msg` | `true` | 用合并转发卡片；关掉就发纯文本 |
| `max_forward_nodes` | `60` | 节点数超过就改用纯文本（QQ 对转发节点数有上限） |
| `bot_uin` | `""` | 转发节点显示的身份 QQ 号。**建议填上**；留空时依赖事件里的号，拿不到会显示成 0 |

`push_targets` 的格式是 `<平台ID>:<消息类型>:<号>`：

```
私聊    aiocqhttp:FriendMessage:<你的QQ号>
群      aiocqhttp:GroupMessage:<群号>
```

平台 ID 以你面板里的平台名为准（有的实例显示成中文名）。

### 天气（2 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `weather_enabled` | `true` | 关掉就不取天气 |
| `weather_city` | `"Chongqing"` | 传给 wttr.in 的城市名 |

### 大模型（3 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `llm_provider` | `""` | **可留空** = 跟随 AstrBot 全局默认模型。想给简报换个更便宜的小模型时才填 |
| `llm_max_items_per_cat` | `8` | 每个分类最多喂给模型几条。**超出的不会丢** —— 下一轮它们仍在「新的」里，会重新进 prompt；当轮会在正文末尾注明还有几条没排上。填 `0` = 不限 |
| `llm_timeout_seconds` | `60` | 超时就降级成纯列表 |

### 抓取（6 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `request_timeout_seconds` | `20` | 单个 HTTP 请求超时 |
| `max_items` | `80` | 每个源最多取几条 |
| `enable_campus` | `true` | 抓校内通知 |
| `enable_competition` | `true` | 抓竞赛 |
| `fetch_body_campus` | `true` | **建议保持开启**——时间/地点/要求基本只在正文里 |
| `fetch_body_competition` | `false` | 竞赛默认只抓列表页摘要 |

### 安全（7 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `command_allow_from` | `[]` | **管理员 QQ 号**，可用全部指令。默认空 = 谁都不能用，**必须先填上自己的号** |
| `command_allow_groups` | `[]` | **开放查询的群号**。名单里的群，任何人都能 `/digest`。默认空 = 群里谁都不能查 |
| `query_recent_days` | `30` | 公开查询只看最近多少天 |
| `query_notify_admin` | `true` | 群友查到新通知时，同时给管理员私聊发一份 |
| `query_all_max_items` | `40` | `/digest all` 最多列几条，超出会提示还有几条没列 |
| `queue_limit` | `3` | 最多容忍几个人排队，超出直接劝退 |
| `query_cooldown_seconds` | `120` | 同一会话的查询冷却秒数 |

**默认锁死是刻意的**：插件的默认值会跟着仓库一起公开，若写成「留空即全开」，别人装完忘了配就等于把 `/digest now` 对外敞开——那玩意会烧 API 额度、还会往群里发消息。

### 群消息（10 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `group_capture_enabled` | `true` | 总开关。关掉就完全不监听群消息 |
| `group_capture_hours` | `24` | 缓冲窗口。超过这个时间的消息丢掉 |
| `group_max_buffer` | `500` | 缓冲上限条数 |
| `group_allow_from` | `[]` | 只采集这些群。**留空 = 机器人所在的每个群都抓** |
| `group_keywords` | `[]` | 留空 = 群里的消息全要；填了只保留含关键词的（按内容筛，不区分群） |
| `enable_group_forward` | `true` | 群消息参与简报生成 |
| `group_block_same_sender` | `true` | 分块要求同一发送者。**开**：群友回复会被分到别的块，不会跟着转出去；**关**：只看时间（适合两个人接力发一条通知的群） |
| `group_aggregate_minutes` | `10` | 同群、相邻两条间隔不超过这么久就当成同一条通知的几段 |
| `group_end_keywords` | `[]` | 「结」白名单（**整条精确等于**才算）。留空 = 内置的 结/已结/截止/已截止/结束/已结束/截止了/已截止了 |
| `group_end_contains` | `[]` | 「结」包含词（**引用了别人**且不超过 10 字时按包含判）。留空 = 内置的 截止/结 |

### 到期提醒（3 项）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `deadline_alert_enabled` | `true` | 插【即将截止】那一段 |
| `deadline_alert_days` | `7` | 距截止还有几天内开始提醒 |
| `no_due_expire_days` | `30` | 没有截止日的条目，入库多少天后算过期（同时也是条目库的「有效」判据） |

## 五、指令

| 指令 | 作用 | 谁能用 |
|---|---|---|
| `/digest`（或 `/digest query`） | 只查增量：有新通知才现算，没有就回「新增 0 条」 | 管理员 + 开放群里的任何人 |
| `/digest all` | 把条目库里所有没过期的都发一遍（直接拼，**零模型消耗**） | 同上 |
| `/digest help` | 使用说明 | 同上 |
| `/digest now` | 立即跑一次完整流程并推送 | 管理员 |
| `/digest test` | 完整重走一遍（抓网页 + 调模型），**不推送、不写库** | 管理员 |
| `/digest status` | 看当前状态（库多少条、下次几点推、机器人号……） | 管理员 |
| `/digest reset` | 清数据，见下 | 管理员 |

`/digest reset` 需要带词才执行，三个动作各自独立：

| 写法 | 清什么 | 影响 |
|---|---|---|
| `/digest reset seen` | 去重基线 | 下次推送会把窗口内的都当新的。积压如果超过单次上限（`llm_max_items_per_cat`），会**连着几轮推完**，一条都不会丢 |
| `/digest reset store` | 条目库 | 会随推送慢慢重新积累；去重基线不受影响 |
| `/digest reset group` | 群消息缓冲 | 只影响还没推出去的那批 |

不带词会列出上面这个菜单。

## 六、权限

两个名单管的事不一样：

| | 填什么 | 能干什么 | 留空时 |
|---|---|---|---|
| `command_allow_from` | **QQ 号** | 全部指令 | 谁都不能用 |
| `command_allow_groups` | **群号** | 群里**任何人**都能 `/digest` 现算一份 | 群里谁都不能查 |

不在任何名单里的会话发指令时，插件**一个字都不回**，并且会 `stop_event()` 把这条消息截断——不这样做的话，消息会继续流向别的插件和 AstrBot 的 AI 对话，机器人照样会在群里冒泡。

推送范围同理：`_push` 只遍历 `push_targets`，没列进去的会话一个字节都发不出去。机器人被拉进新群不会自动开口。

### 「收」和「发」是两码事

| | 管什么 | 配置项 | 留空时 |
|---|---|---|---|
| **收**（看） | 采集哪些群的消息 | `group_allow_from` | **全抓**——机器人所在的每个群都收 |
| **发** | 简报推到哪些会话 | `push_targets` | 一个都不发 |

两者互不绑定：可以「收 3 个群的消息，只发到 1 个私聊」，这是推荐用法。

> 「收」还隔着一层平台：机器人得**已经被拉进那个群、且协议端能收到该群消息**（群没被禁言），插件这边才谈得上收。`group_allow_from` 是在「已经收得到」的前提下再筛一层。

## 七、输出形态

### 7.1 合并转发卡片

默认形态。结构：

```
每日简报 2026-10-12          <- 头部（含天气）
────────────────             <- 分隔线
【校内通知】
  [通知标题一]
  内容简述：……
────────────────
【竞赛】
  [竞赛标题]
  ……
────────────────
【群消息转发】
  [张三：关于举办XX的通知]
  ……                        <- 这条条目下方嵌一张内嵌卡片
```

**内嵌卡片**：群消息那一条，原文会被做成一张子卡片（里面是这个块的原始消息和图片）。一个块算一个节点。

### 7.2 降级

节点数超过 `max_forward_nodes`、或协议端不支持合并转发时，自动退回纯文本（内嵌卡片展开成原文）。**降级原因会写在回复里**，不会静默。

## 八、维护指南

改完**都要在面板点「重载插件」**（或重启 AstrBot）才生效——插件只在加载时读一次配置。

### 8.1 改配置

面板改最省事。打不开面板时可以直接改文件：

```
<实例目录>/core/data/config/astrbot_plugin_cqu_daily_digest_config.json
```

> 手改 JSON 时**数组要写成 `["a", "b"]`**，不能写成 `"a, b"` 这种字符串——类型不对的配置项会被当成空值处理。白名单尤其如此，写错就等于把自己锁在门外。
>
> 整数配置填**负数或明显超出范围**的值（比如 `max_digest_chars` 填 `-5`）会被当成默认值处理，而不是照单执行 —— 免得出现「设了但没生效」这种看不出来的情况。

### 8.2 改「摘什么」的判断标准

「哪些算跟学生相关」写在 `cqu_digest/digest/renderer.py` 顶部的 `SYSTEM_PROMPT` 里，是一段给模型看的自然语言。想调整保留/丢弃的范围，改这段文字即可。

**改提示词时的注意事项**：

- 里面关于**条目格式**的硬要求不要动（`[标题]` 那一套）。格式一变，`entries.py` 的解析就配不上了
- **原文没写的字段要整行省略**这条也别改——加上「未提及」会让简报很长而且没有信息量
- 改完用 `/digest test` 看一眼输出，确认「时间：」「地点：」这些行还在

### 8.3 改完怎么验证

| 指令 | 用途 |
|---|---|
| `/digest test` | 立刻看简报长什么样，**不推送、不写库** —— 调提示词最先用这个 |
| `/digest status` | 看配置有没有生效（推送时间、开关、库里的条数） |
| `/digest now` | 真跑一次并发出去 |

改配置 / 提示词不生效，九成九是**忘了重载插件**。

### 8.4 常见故障

| 现象 | 先查什么 |
|---|---|
| 群里发指令毫无反应 | `command_allow_groups` 里有没有这个群号（注意是**数组**不是字符串） |
| 定时不推 | `push_enabled` / `push_targets` 是否为空 / `push_time` 是不是写成了全角冒号 |
| 收到纯文本而不是卡片 | 节点数是否超过 `max_forward_nodes`；或 `bot_uin` 没填。原因会写在回复里 |
| 转发卡片里群消息没有原文卡片 | `enable_group_forward` 是否为 true；群里有没有发过「结」把块关掉 |
| 简报里全是行政公文 | `fetch_body_campus` 关了，模型只能靠标题判断 → 打开它 |
| 重载后行为没变 | 重启 AstrBot（子包缓存） |

## 九、加一个信息源

编辑 `cqu_digest/fetch/sources.py`，往 `SOURCES` 里加一个 dict：

```python
{
    "key": "cqu_xxx",              # 唯一标识。改了它，该源已推条目会重推
    "name": "重庆大学XXX",          # 简报里显示的名字
    "url": "https://...",          # 列表页
    "selector": "ul.list li a",    # 命中列表里每条条目的 CSS 选择器
    "parser": parse_text_content,  # 从标签里抠标题的函数，见 parsers.py
    "category": "campus",          # campus | competition
    "base_url": "https://...",     # 相对链接补全用
    "excerpt_selector": "p.desc",  # 可选：列表页自带的摘要节点（省一次详情页请求）
    "article_selector": "div.v_news_content",  # 可选：详情页正文容器
}
```

`article_selector` **强烈建议配**。不配的话抓正文会退回整页文本，前 1500 字全是导航菜单，跟正文毫无关系。配了之后容器没命中就宁可返回空串，也不退回整页。

`excerpt_selector` 的摘要可能是链接的**兄弟节点**而不是子节点（如 `<a class="title">…</a><p class="desc">…</p>`），插件会先在本条目里找、再往上一层父节点找。

加完用 `/digest status` 看每个源配好没有。

## 十、数据存在哪

五张表都存在 AstrBot 的 KV 里（`core/data/data_v4.db`，所有插件共用）：

| 表 | 内容 | 上限 |
|---|---|---|
| `seen_ids` | **已经推给管理员看过**的通知 id | 800 |
| `entries` | 条目库（结构化记录） | 400 |
| `group_buffer` | 群消息缓冲（还没聚块推出去的） | 500 条 / 24 小时 |
| `digest_last` | 上次真推出去的原文（留档） | 1 份 |
| `last_run_date` | 上次跑的日期（启动补推判断） | — |

只在内存里、重启就没的：查询冷却缓存、排队计数。

**占用很小**：全部攒满大约 0.8 MB。

## 十一、首次运行

第一次跑（`seen_ids` 为空）**只会把当前抓到的条目记为基线，不推送**——否则第一次会把整站历史一次性刷给你。之后再跑推的就是真正的增量。

## 十二、已知限制

- **群版合并转发未实机验证过**。私聊版在 NapCat 上实测可用；群版没试过，失败会自动退回纯文本（功能不受影响，只是形态变了）。
- **内嵌卡片依赖协议端**。Node 里套 Node 的写法在 NapCat 上实测可用，其他协议端不一定。
- **「结」的判据是猜的**。通知群实际怎么发「结」还没实测，`group_end_keywords` / `group_end_contains` 留了开关，实测后按需要加词。
- **`/digest all` 的条数上限**：库大了不能一次全倒出来（转发节点数会超），超出会提示还有几条没列。
- **只支持 OneBot v11 系协议端**（依赖合并转发和 Node 消息段）。
